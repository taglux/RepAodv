# REP-AODV — репутационный протокол маршрутизации для MANET

Реализация протокола **REP-AODV** в среде моделирования OMNeT++ / INET 4.5.4.
Цель проекта — разработка надежного механизма обнаружения и изоляции вредоносных узлов-поглотителей (атака типа Blackhole) в беспроводных самоорганизующихся сетях (MANET) с использованием распределенной репутационной системы на базе Байесовской машины доверия и механизма эстафетного подтверждения (2ACK).

---

## 1. Введение и проблематика

### Особенности сетей MANET и уязвимости AODV
Беспроводные самоорганизующиеся сети (MANET) функционируют без централизованной инфраструктуры. Узлы выступают одновременно в роли конечных устройств и маршрутизаторов. Протокол AODV (Ad hoc On-Demand Distance Vector) использует реактивный подход: маршрут устанавливается исключительно по требованию. 
Процесс поиска маршрута (Route Discovery) обладает следующими уязвимостями:
1. Узел-источник инициирует широковещательный запрос `RREQ` (Route Request).
2. Узел, располагающий маршрутом к целевому узлу (или сам целевой узел), отвечает сообщением `RREP` (Route Reply), указывая количество транзитных узлов (`HopCount`) и порядковый номер пункта назначения (`DestSeqNum`), который гарантирует актуальность маршрута.
3. Узел-источник выбирает маршрут с наибольшим значением `DestSeqNum` и наименьшим `HopCount`.

### Атака типа Blackhole (Узел-поглотитель)
При реализации атаки типа Blackhole вредоносный узел немедленно отвечает на любой перехваченный запрос `RREQ` поддельным сообщением `RREP`. В данном ответе злоумышленник заявляет минимальное расстояние (`HopCount = 1`) и искусственно завышенный номер `DestSeqNum` (как правило, максимально возможное значение). 
Согласно спецификации протокола AODV, узел-источник обязан выбрать данный маршрут как наиболее актуальный и кратчайший. После перенаправления трафика на себя, вредоносный узел преднамеренно отбрасывает все проходящие через него пакеты данных. При отсутствии механизмов защиты коэффициент доставки пакетов (Packet Delivery Ratio, PDR) в сети снижается до 0–2% даже при наличии всего 10% вредоносных узлов.

### Предлагаемое решение: REP-AODV
Протокол REP-AODV модифицирует базовую логику маршрутизации, интегрируя дополнительный уровень мониторинга и оценки доверия. Вместо безусловного доверия к получаемым маршрутным ответам, узлы сети накапливают информацию об успешности передачи данных соседними узлами. Процесс маршрутизации становится зависимым от репутации: маршруты, проходящие через ненадежные узлы, пессимизируются метрикой стоимости или полностью блокируются.

## 2. Архитектура системы

Предлагаемый протокол состоит из трех взаимосвязанных подсистем:
1. **Подсистема детектирования (2ACK Relay):** Обеспечивает объективный мониторинг успешности пересылки пакетов на сетевом уровне (L3). Формирует первичные данные (доказательства) о поведении узлов.
2. **Байесовская машина доверия (Trust Engine):** Математический аппарат, осуществляющий агрегацию полученных доказательств, вычисление непрерывной метрики доверия (Reputation) и управление конечным автоматом состояний (State Machine) для каждого соседнего узла.
3. **Подсистема обмена репутацией:** Отвечает за распространение информации об обнаруженных угрозах в сети с целью превентивной изоляции злоумышленников.

---

## 3. Математическая модель доверия (Bayesian Trust Engine)

Переход от применения простых экспоненциальных скользящих средних (EMA) к Байесовскому выводу обусловлен необходимостью строгого учета степени неопределенности и исторического контекста взаимодействий.

### Бета-распределение
Репутация узла моделируется посредством вероятностного распределения `Beta(α, β)`. 
Данный подход оптимален для описания вероятности бинарных событий (успешная пересылка или потеря пакета).
*   `α` (альфа) — накопленный положительный опыт (количество успешно пересланных пакетов).
*   `β` (бета) — накопленный отрицательный опыт (количество отброшенных пакетов).

В протоколе используются априорные значения `α_prior = 2.0` и `β_prior = 1.0`, что обеспечивает начальную оценку доверия в условиях отсутствия наблюдений:
`E = α / (α + β) = 2.0 / 3.0 ≈ 0.67`

### Обновление параметров
При поступлении нового доказательства от подсистемы детектирования, параметры распределения обновляются:
*   При подтверждении успешной доставки: `α = α + weight`
*   При фиксации потери пакета: `β = β + weight`

Весовой коэффициент (`weight`) зависит от источника информации. Прямое наблюдение (Direct Evidence) имеет максимальный вес (1.0). Косвенные наблюдения, полученные от соседних узлов, обладают сниженным весом (0.5), что необходимо для демпфирования распространения ложной информации.

### Экспоненциальное затухание (Time Decay)
Учитывая динамичную природу топологии сети, устаревшие данные (например, потери, вызванные временными радиопомехами) должны со временем утрачивать актуальность. Реализован механизм экспоненциального затухания (Time Decay): при отсутствии новых взаимодействий в течение заданного временного окна (`evidenceHalfLife`), параметры `α` и `β` асимптотически возвращаются к своим априорным значениям.

## 4. Механизм эстафетного подтверждения (2ACK Relay)

Для обеспечения гарантии того, что узел не только получил пакет, но и осуществил его дальнейшую ретрансляцию, применяется механизм эстафетного подтверждения.

Рассмотрим маршрут передачи: `A -> B -> C`. 
Узел `A` передает пакет узлу `B` в ожидании его ретрансляции к узлу `C`. Стандартное подтверждение на канальном уровне (MAC ACK) удостоверяет лишь факт доставки до узла `B`. В рамках механизма 2ACK узел `C` (получатель второго перехода) обязан инициировать специальное подтверждение для узла `A`. В реализованной эстафетной модели (Relay-подход) узел `C` подтверждает получение узлу `B`, после чего узел `B` ретранслирует данное подтверждение (сообщение `2ACK_RELAY`) обратно к узлу `A`.

### Проблема ложных срабатываний и механизм перенаправления вины (Blame Redirect)
В случае если узел `C` является вредоносным (узел-поглотитель), он не сформирует подтверждение. В результате узел `A`, не получив сообщение `2ACK_RELAY` от узла `B`, может ошибочно классифицировать корректно функционирующий промежуточный узел `B` как вредоносный (False Positive).

Для устранения данного состояния гонки (Race Condition) между таймерами ожидания, в протоколе REP-AODV реализован **механизм вложенных тайм-аутов, зависящих от значения времени жизни пакета (TTL)**:
`timeout = 0.2 + (TTL * 0.01) секунд`

Поскольку значение TTL декрементируется при каждом переходе, тайм-аут ожидания на узле `B` истечет раньше, чем на узле `A`. 
При срабатывании тайм-аута на узле `B` в отношении узла `C`, узел `B` фиксирует потерю пакета. В этот момент узел `B` в принудительном порядке генерирует сообщение `2ACK_RELAY_RECOVER` и направляет его узлу `A`. 
**Результат:** Узел `A` получает достоверное подтверждение того, что узел `B` корректно выполнил свою функцию (и фиксирует положительный опыт для `B`), в то время как узел `B` фиксирует отрицательный опыт в отношении узла `C`. Данный подход обеспечивает защиту корректно функционирующих узлов от неправомерной изоляции.

## 5. Управление состояниями (State Machine)

Вместо бинарной логики "надежный/заблокированный", протокол REP-AODV использует четырехуровневую конечную модель состояний. Переходы между состояниями детерминируются текущим математическим ожиданием репутации и счетчиком прямых потерь (`directNegativeCount`).

1. **Надежный (Trusted):** `Репутация > suspectThreshold`. Узел функционирует в штатном режиме.
2. **Подозреваемый (Suspect):** `quarantineThreshold <= Репутация <= suspectThreshold`. 
   Выполняется "мягкая" инвалидация: протокол инициирует рассылку сообщений `RERR` для маршрутов, проходящих через данный узел, стимулируя поиск альтернативных путей. Полной блокировки узла не происходит, и он может быть задействован при отсутствии иных маршрутов.
3. **Карантин (Quarantine):** `Репутация < quarantineThreshold`. 
   Строгая изоляция. Пакеты, адресованные данному узлу, отбрасываются. Узел исключается из процессов формирования маршрутных ответов `RREP`. Продолжительность карантина определяется параметром `quarantineWindow` (по умолчанию 60 секунд).
   *   **Процедура реабилитации:** По завершении периода карантина узел переводится в состояние `TRUSTED` с частичным сохранением накопленного отрицательного опыта (параметр `beta`). Пороги чувствительности для последующей изоляции снижаются. При возобновлении отбрасывания пакетов узел подвергается ускоренной повторной изоляции (Fast-retrack).
4. **Изолированный (Permanent):** Окончательная блокировка. Состояние достигается при исчерпании лимита циклов карантина (`maxQuarantineCycles`), ЛИБО при накоплении критического объема *прямых* доказательств потери пакетов (`minDirectEvidence`). Процедура выхода из данного состояния не предусмотрена.

## 6. Протокол обмена репутацией

В целях ускорения локализации злоумышленников (особенно на удаленных участках сети) узлы с установленной периодичностью (каждые 10 секунд) осуществляют рассылку векторов недоверия (`AodvTrustShare`). Вектор инкапсулирует информацию о соседних узлах, находящихся в состоянии `SUSPECT` или ниже.

**Механизм защиты от компрометации репутационных данных:**
*   **Фильтрация по уровню доверия:** Узел принимает информацию исключительно от соседей, классифицированных как `TRUSTED` и обладающих высокой репутацией (`> gossipThreshold`).
*   **Дифференциация весовых коэффициентов:** Косвенное наблюдение (`SIGNED_HINT`) увеличивает значение отрицательного опыта (`beta`) с коэффициентом, вдвое меньшим по сравнению с прямым наблюдением.
*   **Блокировка самообвинения:** Узлы игнорируют входящие репутационные пакеты, содержащие негативные оценки в их собственный адрес.
*   **Изоляция косвенных доказательств:** Информационный обмен влияет на общую оценку репутации (что может инициировать переход в состояние карантина), однако **не** модифицирует счетчик прямых потерь (`directNegativeCount`). Следовательно, косвенные наблюдения математически не способны инициировать перевод корректно функционирующего узла в состояние `PERMANENT`.

## 7. Топология моделирования и результаты

**Параметры моделирования:** Топология в виде регулярной решетки 5×4, 20 транзитных узлов + 1 узел-приемник. Расстояние между узлами составляет 200 м. Доля вредоносных узлов — 10% (2 узла из 20). В сети инициируются два независимых UDP-потока данных. Каждая конфигурация воспроизводится 10 раз при различных значениях начального зерна генератора псевдослучайных чисел (N=10); в таблице приведены среднее арифметическое и стандартное отклонение.

Разработано 5 тестовых сценариев (RA1–RA5) с различным пространственным распределением атакующих узлов:
*   **RA1 (Центр):** Вредоносные узлы располагаются в узловых точках пересечения информационных потоков.
*   **RA2 (Периферия):** Вредоносные узлы расположены вблизи узлов-получателей, что снижает их видимость для транзитных узлов.
*   **RA3 (Критический маршрут):** Атака направлена на узлы, непосредственно смежные с источниками трафика.
*   **RA4/RA5 (Смежные/Диагональные):** Специфические топологические конфигурации для оценки поведения протокола при атаке на пары узлов с высокой взаимной близостью.

**Коэффициент доставки пакетов (PDR) и среднее время обнаружения (статическая топология, N=10):**

| Сценарий | PDR, базовый AODV | PDR, REP-AODV | Время обнаружения, с |
|---|---|---|---|
| Без атаки | 99.2 ± 0.5% | 89.6 ± 2.4% | — |
| RA1 (Центр) | 29.4 ± 33.9% | **70.8 ± 3.0%** | 18.0 ± 6.0 |
| RA2 (Периферия) | 29.5 ± 33.8% | **88.1 ± 2.9%** | 17.8 ± 3.3 |
| RA3 (Крит. маршрут) | 5.1 ± 15.8% | **80.5 ± 7.8%** | 16.7 ± 5.2 |
| RA4 (Смежные) | 29.7 ± 25.5% | **76.9 ± 6.2%** | 19.0 ± 4.2 |
| RA5 (Диагональные) | 35.1 ± 33.6% | **79.4 ± 14.1%** | 26.6 ± 33.5 |

*Примечание: Снижение PDR в сценарии без атакующих с 99.2% до 89.6% обусловлено накладными расходами репутационной подсистемы (служебный трафик механизма 2ACK и периодические рассылки gossip-векторов). Высокое стандартное отклонение показателей базового AODV при наличии атаки объясняется зависимостью PDR от случайного выбора маршрута: при обходе вредоносного узла значение PDR приближается к 99%, при попадании в него — к 0%.*

**Основной результат:** Совокупное применение механизма перенаправления вины (Blame Redirect) и дифференциации весовых коэффициентов доказательств обеспечивает **полное отсутствие ложных срабатываний** для корректно функционирующих узлов во всех статических сценариях RA1–RA5 (N=10).

## 8. Архитектура программной реализации

Интеграция протокола в фреймворк INET выполнена прозрачно, с максимальным сохранением оригинальной кодовой базы протокола AODV. 

**Структура директории `src/repaodv/`:**
*   **`Aodv.cc / Aodv.h`:** Основной класс `RepAodv`, наследующий базовую реализацию `inet::aodv::Aodv`. Содержит переопределенные точки перехвата (hooks) для обработки пакетов `datagramForwardHook`, `datagramLocalOutHook` и методы маршрутизации `handleRREP`, `handleRREQ`.
*   **`repAodv.msg`:** Декларация пользовательских форматов сообщений (структуры для механизма 2ACK и векторов обмена репутационной информацией).
*   **`trust/TrustEngine.cc / .h`:** Фасад репутационной подсистемы. Обеспечивает хранение контекста оценки (TrustView) для каждого соседнего узла.
*   **`trust/TrustPolicy.cc / .h`:** Программная реализация математического аппарата Байесовского обновления, функции затухания и переходов конечного автомата. Данный модуль изолирован от сетевого уровня.
*   **`trust/detectors/TwoAckDetector.cc / .h`:** Модуль мониторинга эстафетных подтверждений. Реализует логику таблицы ожидаемых пакетов `ackRelayTable` и формирование событий по истечению тайм-аутов с функцией перенаправления вины.

## 9. Инструкция по сборке и запуску

### Зависимости
*   Среда моделирования OMNeT++ версии 6.x
*   Библиотека INET Framework версии 4.5.4 (директория библиотеки должна располагаться на одном уровне с директорией проекта: `../inet-4.5.4`)

### Компиляция проекта
Для сборки проекта используется стандартная утилита среды OMNeT++ (`opp_makemake`):
```bash
make -j$(nproc)               # Компиляция оптимизированной версии (Release)
make MODE=debug -j$(nproc)    # Компиляция версии для отладки (Debug)
```

### Выполнение индивидуального сценария
Для запуска сценария с использованием графического интерфейса Qtenv или в консольном режиме (Cmdenv):
```bash
cd simulations
# Запуск нулевой итерации (seed 0) сценария RA1 в консольном режиме
./run omnetpp.ini -c AttackTestRA1 -r 0 -u Cmdenv
```

### Пакетное выполнение и анализ результатов
Для последовательного запуска всех конфигураций (по 5 итераций для каждого сценария) с последующим автоматическим анализом журналов:
```bash
cd simulations
bash run_benchmarks.sh
```

По завершении процесса моделирования агрегированные результаты (значения PDR, временные задержки, статистика изолированных узлов) выводятся в консоль и сохраняются в формате CSV в директории `simulations/result/`. Для детального анализа сформированного журнала (log) предусмотрен специализированный скрипт:
```bash
python3 simulations/result/analyze_log.py simulations/result/simulation_log.csv
```
